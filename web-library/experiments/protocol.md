# Протокол первого эксперимента v0.2

## Вопрос и гипотеза

Вопрос: уменьшает ли наш пакет число конкретных исправлений по сравнению с тем же брифом без пакета? Предполагаемый механизм — более явный выбор композиции и обработка скролл-состояний. Это гипотеза, не установленная причина предыдущих неудач.

Основной кандидат для сравнения: `core` против `profile`. Одинаковы бриф, контент, инструменты, время и общее ядро с проверками; различается специализированный пакет. `baseline` — дополнительный ориентир «бриф + ограничения», не обязательный третий запуск при ограниченном бюджете.

Единица вывода — конкретная модель + среда + версия пакета + класс брифа, не «агенты вообще». Исследования контекстных файлов измеряют разные результаты и не доказывают улучшение веб-дизайна: основания и ограничения собраны в `web-library/resources/research-v0.2.md`.

Даже core→profile добавляет несколько правил: это оценка пакета в целом, не доказательство пользы каждого модуля или внешнего репозитория. Если разница полезна, следующий эксперимент отключает только один модуль при неизменном остальном. Не заменять такой разбор большой таблицей одновременно меняющихся условий.

## Перед запуском

1. Проверить сохранность библиотеки после синхронизации и выполнить validator.
2. Зафиксировать версию, пакеты и JSON-манифесты. Сохранить копию входов: SHA-256 не позволяет восстановить утраченное содержимое.
3. Записать точное доступное обозначение модели, параметры если известны, инструменты и версии, дату, бюджет 45 минут и максимум два пользовательских раунда. Эти числа — первоначальные ограничения теста, не обещание достаточности; менять только для следующей серии.
4. Согласовать что считать существенной правкой. По умолчанию: сломанный сценарий, нечитаемый/скрытый материал, неуместная композиция, необходимость заменить основной визуальный замысел. Локальное предпочтение оттенка отмечать отдельно.
5. Выбрать один бриф: `fold`. `archive` — второй development-кейс для будущей проверки переноса, не закрытый тест.

До первого запуска записать основной исход: число результатов, принятых человеком к концу второго пользовательского раунда без блокеров T01–T12, делённое на число всех запущенных попыток. Срывы бюджета, незавершённые результаты и отказы не удалять из списка; причину отмечать отдельно. При not_run браузера/человеческой оценки сообщать «недостаточно данных», а не оценивать долю визуального успеха. Для отдельного принятого пилота это наблюдение, не доказанная эффективность системы.

Вторичные показатели: существенные правки после первого варианта, четыре визуальные оси, время и доступный расход токенов. Не выбирать задним числом единственную удачную метрику. Ухудшение по блокерам не компенсируется уменьшением времени.

## Изоляция

Запускать варианты в новых сеансах с одинаковыми системными/проектными ограничениями. Передавать только свой самодостаточный пакет. Не давать исходники текущего сайта, другой вариант, отчёты оценщика и историю этого чата. Не подключать библиотечный скилл к контрольному варианту автоматически.

Если среда не позволяет изолировать контекст или агент уже видел библиотеку, отметить contamination и считать результат демонстрацией. Автоматический сборщик не запускает отдельные модели и не обеспечивает изоляцию сам.

Проверить фактически переданные инструкции, автоподключённые скиллы и память сеанса, а не только название «новый чат». Если изоляция не подтверждена, установить context_contaminated=true или null, но не false по предположению. Использовать одинаковый доступ к веб-источникам в обоих вариантах; записывать URL и причину каждого чтения в source_reads. Разное число реально прочитанных справок — часть эффекта пакета и его стоимости, а не бесплатное улучшение.

Сохранять каждый повтор отдельно, например `trial-output/fold-profile-r1/`. Путь в пакете без r1 — начальный; для повтора сделать отдельную рабочую копию, не перезаписывать предыдущий результат. При нескольких повторах чередовать порядок вариантов. Два-три повтора полезны как разведка разброса, но не дают статистической гарантии.

## Что оценивать

Первый снимок результата фиксировать ДО пользовательской коррекции. Записать пройденные/проваленные/невыполненные проверки из review, время и внутренние переделки. Размер файла — описательная метрика, не оценка красоты или FPS.

Человек просматривает варианты с нейтральными обозначениями A/B, по возможности не зная условий. Даёт четыре отдельных визуальных балла из `web-library/checks/review.md`, список конкретных правок и решение «принимаю / нужна существенная доработка». Самооценка создавшего агента не заменяет эту оценку.

Во втором пользовательском запросе передавать консолидированный список выявленных дефектов, а не новые требования, референсы или другой контент. Если требования изменились — это новая задача, не успех/провал прежнего пакета. Сохранить точный текст коррекции и повторить проверки.

## Формат результата

Скопировать `web-library/experiments/run-template.json` для каждого запуска и заполнить реальными значениями. Неизвестные числовые значения оставлять null, не 0. `not_run` не считать pass. Для ручной оценки нужны экран/состояние и обоснование. Статусы внутри шаблона не являются уже полученными результатами.

Формат одного checks: `{ "id": "T04", "round": 1, "status": "pass", "evidence_path": "trial-output/fold-profile/keyboard-review.md" }`. Для not_run evidence_path можно не задавать. Браузерное и человеческое свидетельства хранятся отдельно как `{ "round": 1, "path": "trial-output/fold-profile/review.md" }`; в файле нужны действия/наблюдения и автор оценки. Исполнитель не заполняет человеческую приёмку сам.

Поля visual_scores относятся к первому результату, second_visual_scores — ко второму. Не затирать первый результат после коррекции. Статус completed означает завершённую генерацию, а не пройденную приёмку. Для true в принятии соответствующего раунда нужны все T01–T12 pass, визуальные оценки и оба вида свидетельств. Команда `python web-library/tools/library.py.txt check-run --report web-library/experiments/run-template.json` проверяет структуру пустого шаблона; для реального запуска указать его файл. Валидатор проверяет наличие и согласованность записей, не истинность наблюдений и не качество дизайна.

До браузерной и человеческой приёмки допускается вывод «пакеты воспроизводимо собираются», но не «сайты стали лучше». Если ресурсов на A/B нет, сначала сделать один pilot: проверить ясность задания, экспорт и возможность оценки, без причинных выводов.

## Перенос и закрытая проверка

После первых запусков разобрать ошибки по категориям: бриф / визуальный выбор / контент / реализация / проверка / среда. Улучшать только подтверждённый пробел. Затем проверить `archive`, не добавляя для него скрытые подсказки в ядро.

Настоящий holdout подготовит оценщик после заморозки версии, вне контекста настройщика. Здесь его текста нет намеренно. После обсуждения его ошибок он перестаёт быть закрытым и для следующего цикла понадобится другой.

## Правило решения после пилота

Для небольшого числа попыток показать каждую пару и все причины отказа; не писать статистическую значимость без подходящего расчёта и достаточных данных. Если profile не помогает или его затраты заметно выше, сохранить более простой core. Изменять одно предполагаемое полезное правило и повторять сравнение, не наращивать библиотеку автоматически. Успех на fold не повышает источник до recommended и не подтверждает перенос на дашборды.
